# KeyMelier 1.9 – Make errors understandable and manageable

Status: assignment, not implemented yet. As of 2026-09-28.

## Goal

Improve the error handling of existing flows in KeyMelier. Users should understand what happened and which action helps them. The scope stays limited to small improvements to messages, status displays and retry actions.

KeyMelier remains a management and diagnostic tool for security keys. This assignment complements the plan for reliable key recognition in [1.9-key-identity.md](1.9-key-identity.md).

## Boundaries

- Do not add penetration-testing features, interception, tampering interfaces or WebAuthn decoders.
- Do not trigger additional hardware checks automatically at start, when showing details or after an error.
- No new export functions or copyable technical details in this assignment.
- Do not require signing, certificate procurement or any other manual infrastructure task.
- Do not weaken existing checks or security requirements to make a flow appear successful.
- No unrelated changes and no large architecture migration.

## Task 1 – Review the current state and record gaps

- [ ] Review the existing error mapping, API responses, UI messages and tests.
- [ ] Check in particular attestation, the function test and the affected PIN/UV flows. Starting points are `fido2tool_core/auth.py`, `fido2tool_core/attestation.py`, `fido2tool_core/function_test.py` and the related UI in `static/app.js`. Verify the actual responsibilities in the repository.
- [ ] For each situation below, record: already correct, incomplete or missing.
- [ ] Close only proven gaps. Reuse correctly handled cases and existing tests.

## Task 2 – Show error states unambiguously

Map provable causes through the existing structured error codes. Do not derive a reliable classification from arbitrary exception texts. If the cause is unclear, use an honest general message.

| Situation | Intended display | Matching action |
| --- | --- | --- |
| Time for the touch ran out | Neutral: "No touch detected. The waiting time has run out." | Try again |
| User cancelled | Neutral: "Cancelled." | Try again, if the operation can be repeated |
| Key removed during the operation | "The connection to the key was lost." | Ask to reconnect; continue only after the device has been identified safely |
| PIN or user verification required | "This operation needs confirmation by PIN or fingerprint." Name only the methods actually available. | Open the existing matching PIN/UV flow |
| Wrong PIN | Understandable error message; show remaining attempts only if reliably known | Deliberate new entry; no automatic retry |
| PIN or user verification blocked | Explain the block and the available safe next step | Do not offer a normal retry if it cannot help |
| Function not supported by the key | Neutral: "This key does not support this function." | No retry button that cannot succeed |
| Evidence missing or check not fully possible | "Authenticity could not be confirmed", plus the known reason | Offer only an action that can fix the specific reason |
| Check returns a provably invalid result | "Check failed", plus the affected check step | Keep the error visible; do not classify it as a mere cancellation |
| Unexpected error | "The operation could not be completed." | Offer a safe retry only if the operation is suitable for it |

The texts describe the content. Adapt them to the application's existing wording, terminology and translation structure.

- [ ] Distinguish "cancelled", "could not be checked" and "check failed" consistently.
- [ ] Neutral states must not be shown as a defective or insecure key.
- [ ] Nor may a neutral state produce a green check result.
- [ ] Earlier successful results must not appear as the current success after a new incomplete check. Mark historical results clearly where needed.

## Task 3 – Complete actions and interaction

- [ ] Offer the helpful next action directly with the message and reuse existing flows.
- [ ] Trigger retries only through a deliberate user action.
- [ ] Prevent duplicate calls while an operation runs; reliably end the loading state after success, cancellation and error.
- [ ] After a lost connection, never silently carry an action over to another connected key. Use the existing device assignment; if unclear, return to the selection.
- [ ] Do not repeat modifying operations automatically when their completion is unclear. Name the unclear state and offer an existing safe way to check the state.
- [ ] Do not convey status through colour alone. Message and action must be reachable by keyboard and perceivable through the existing accessibility structure.
- [ ] Do not put PINs, tokens, credential IDs or other sensitive raw data into new messages or logs. Use existing error codes and data-minimal messages.

## Task 4 – Fully automated regression tests

All new acceptance tests must run without a real security key, touch, PIN entry, external services or new credentials. Use the existing test infrastructure and controlled mocks.

- [ ] Timeout, explicit cancellation and lost connection are handled in traceably different ways.
- [ ] PIN required, wrong PIN and PIN blocked lead to the matching states and actions.
- [ ] Unsupported functions and missing check evidence produce neither a false success nor the statement that the key is defective.
- [ ] Actually invalid check results remain errors. Existing negative tests for signatures, bindings or certificates must still pass.
- [ ] Retry actions produce exactly one new call; merely rendering an error message produces none.
- [ ] Errors and cancellation end the loading state and leave no outdated current success message.
- [ ] A device change does not lead to silently continuing on another key.
- [ ] New error messages contain no sensitive test values.

Tests should check observable behaviour and relevant limits. Do not add tests that only duplicate implementation details or exact wording. Do not test cases that are already covered again.

- [ ] Affected backend and UI tests and the required repository checks pass.
