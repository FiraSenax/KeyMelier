# KeyMelier 1.9 – Reliable key identity (implementation plan)

Status: **plan only** (2026-09-28). Nothing below is implemented. Based on release 1.8.0
(`17eb7e4`) and [ROADMAP.md](../ROADMAP.md).

Markers used throughout:
**[exists]** current behaviour in 1.8.0 · **[new]** proposal · **[verify]** assumption that
must be proven (on hardware where noted) before it is relied on.

---

## 1. Where we are (code and roadmap)

**[exists] Identity today** – `fido2tool_core/history.py`:

- `key_id(record) = sha256(AAGUID | USB serial)[:16]`. The serial comes from the HID
  descriptor (`scanner.py`, `desc.serial_number`) or, for YubiKeys, from yubikit
  (`_apply_vendor_info`).
- The ID is **derived**, so two computers compute the same ID for the same key with a serial,
  and sync merges them without any identity logic. Keys without a serial get
  `sha256(AAGUID|)`: all keys of one model share one entry.
- There is a legacy path: an entry first seen without a serial is re-keyed once a serial
  appears (`_entry_for`, field `replaces`).
- `service.py` exposes `history_id = key_id(record)` per connection. The UI (account model,
  lost-key help, replacement) refers to keys by this ID only.

**[exists] What depends on the ID:**

- the account model: coverage, "only on one key", lost keys (`static/accounts.js`)
- lost state: `lost_since`, `lost_done`
- the replacement plan: `replace.new` points to another entry's ID
- sync: entries merged per `key_id`; `forgotten` tombstones by ID; newest change wins per
  field group; verdicts never imported
- inventory export and diagnostics (counts only)

**[exists] Sync compatibility constraint** (verified in code):

- 1.8's `_clean_entry` keeps **only known fields** and accepts only IDs matching `_ID`
  (16 hex).
- A 1.8 computer in the same sync folder therefore:
  - drops every new field,
  - ignores entries with another ID format,
  - keeps writing to the legacy shared ID.

  1.9 must stay correct with such a peer.

**[exists] Material the plan can build on:**

- The authenticity test already runs `makeCredential` with `rk: false`, with user presence
  (touch), optionally with a PIN token (`attestation.py`). Its credential is discarded today.
- The OpenPGP view reads the AID serial (`openpgp_app.py`). yubikit gives the YubiKey serial.

**Roadmap vs. this assignment:** ROADMAP.md proposed the silent recognition credential plus
smart-card serials. This plan keeps both, but tightens them:

- **Recognition credential:** it counts only with a verified **signature**, not with a mere
  success code.
- **Smart-card serials:** they are **hints**, never proof on their own.
- **Added:** explicit identity states, the assistant, the repair of mixed entries and
  cross-computer conflicts.

## 2. Identity model

### 2.1 Separation of concepts [new]

| Concept | Where | Notes |
|---|---|---|
| **Entry ID** – permanent internal ID | `entry.key_id` (unchanged field name) | Existing entries keep their ID. New entries get a **random** 16-hex ID (same format – see sync constraint). Never derived from evidence again, so it never changes when evidence changes. |
| **Connection** – the key plugged in right now | runtime only (`token.id`, HID path) | Recognition result per connection: `{entry_id or null, state, evidence_used, checked_at}`. Never persisted as identity. |
| **Evidence** – technical identity proofs | `entry.evidence[]` | See 2.2. Kept separately from labels. |
| **Labels** – organisational, user-set | `entry.labels = {name, color, role, set_at}` | Existing `label` migrates into `labels.name`. Shown as "set by you", never as recognition. |
| **Integrity** – trust in the stored content | `entry.integrity` | e.g. `{possibly_mixed: true, reason, since}`; archived legacy entries. |
| **Provenance** – where each piece of content came from | per content section | `read: {at, computer, identity: "confirmed" \| "unconfirmed", complete: bool}`. |
| **Aliases** – merged entries | `aliases: {old_id: {into, at, reason}}` (top level, synced) | References and incoming sync data are resolved through them. |

### 2.2 Evidence kinds and their limits

| Kind | Strength | How obtained | Limits |
|---|---|---|---|
| `recognition_credential` [new] | **cryptographic** | Non-discoverable credential created with a touch, RP ID `keymelier.invalid`. Store credential ID, COSE public key, `created`, the computer that created it. Checked silently with `getAssertion(allowList=[id], up=false)`. **Proof = signature verifies** with the stored public key over `authData ‖ clientDataHash`, rpIdHash matches and UP = 0. | [verify] Silent `up=false` per model. [verify] Default `credProtect` for `rk=false` (level 3 would need UV → "unlock needed"). A reset destroys it. It proves "the key that holds this credential", not a vendor serial. |
| `vendor_serial` [exists, reclassified] | strong | yubikit management serial | Vendor-assigned. [verify] Not user-changeable on supported models. |
| `usb_serial` [exists, reclassified] | strong **unless** downgraded | HID descriptor | [verify] Some vendors ship constant or empty-looking serials (`0`, `000000000000`, repeated). Downgrade to **hint** if (a) the value is in a known-constant list, or (b) two connected keys report the same value at once. |
| `openpgp_aid` / `piv_serial` [new use] | **hint only** | smart-card applets | [verify] Writable on some implementations. The CCID reader cannot be tied to one HID device when several keys are connected – only used while exactly **one** key is connected. Never sufficient alone for recognition or merging. |
| AAGUID, product name, firmware, attestation certificate | **none** (descriptive) | getInfo / MDS | Shared by a model or batch (attestation: ≥100,000 devices by FIDO policy). Used only to pick *candidates*. |
| Label, colour, role, QR label | **none** (organisational) | user | Never shown as recognition. |

**Rule:** only `cryptographic` or non-downgraded `strong` evidence can *recognise* a key or
justify an *automatic merge*. Hints may only narrow candidates or be shown to the user.

### 2.3 Recognition protocol [new]

1. **Candidates:** entries with the same AAGUID and at least one evidence item, not archived
   and not aliased away.
2. **Strong evidence first:** a matching non-downgraded vendor or USB serial → recognised.
3. **Otherwise, silent assertion:** for each candidate with a `recognition_credential`, one
   silent assertion.
   - Signature valid → **recognised (cryptographic)**.
   - `CTAP2_ERR_NO_CREDENTIALS` → "not this candidate". This is conclusive only if the
     model has passed the self-check (step 7).
   - `PIN_REQUIRED` / `PUAT_REQUIRED` / UV needed → **unlock needed**.
   - A keepalive with `UPNEEDED`, a timeout (≈2 s) or any other error → **cancel**
     (`authenticatorCancel`) and mark the connection **not supported / unresolved**. This is
     never "different key".
4. **Once per connection**, never in the polling loop. Maximum ~8 candidates; more → ask
   the user (assistant).
5. **One key, several matches:** proven by cryptographic or strong evidence → **proven same
   key → merge** (section 4.3).
6. **Enrolment** (creating the credential) only with an explicit touch:
   - in the authenticity test (reusing its `makeCredential`, same RP ID from 1.9 on), or
   - in the assistant.

   If the key supports it, it gets `credProtect = 1` [verify].
7. **Self-check after enrolment:** immediately run the silent assertion against the new
   credential on the same connection.
   - If that fails, the model is marked "silent recognition not supported" for this AAGUID
     and firmware (cached, synced as a capability hint).
   - Only then is the credential stored as evidence.

   This proves per device that step 3 works before relying on it.

### 2.4 Visible states and transitions [new]

States per **connected key**:

| State | Shown as | Counts as confirmed identity? |
|---|---|---|
| `recognised` | "Technically recognised" + kind and date of proof | yes |
| `unlock_needed` | "Recognition possible after unlocking" | no |
| `unassigned` | "Not yet assigned" | no |
| `unsupported` | "Recognition not supported by this key" | no |
| `conflict` | "Assignment contradictory" | no |
| `new_confirmed` | new entry, just enrolled and self-checked | yes |

Flag per **entry**: `possibly_mixed` → "Earlier data possibly mixed".

Transitions (anything not listed is not allowed):

```
connect ─► candidates? ─ none (all candidates conclusively "not this", or no candidates)
        │                   └─► unassigned ─(assistant: touch + enrol + self-check)─► new_confirmed
        ├─ one proof ───────────► recognised
        ├─ ≥2 proofs, all cryptographic/strong for the same connection ─► merge ─► recognised
        ├─ proofs point to entries with contradicting lost/replacement state ─► conflict
        ├─ UV needed ───────────► unlock_needed ─(user unlocks; PIN once, no retry)─► re-check
        ├─ timeout/UP needed/error/unsupported model ─► unsupported (or unassigned if no proof ever possible)
        └─ candidates without any evidence (legacy) ─► unassigned (never auto-assigned)
unplug at any point ─► result discarded, nothing written
recognised ─(key reset: all its credentials now "not this")─► unassigned  (old entry untouched)
```

## 3. User flows

### 3.1 Assistant "Which key is this?" [new] (priority 3)

1. **List:** connected keys that are not `recognised`, with their state and why.
2. **One at a time:** if more than one unassigned key of the same model is connected, ask
   to leave only one plugged in. It is required when smart-card hints would be used, and
   recommended otherwise: the touch prompt goes to one HID device and only that key
   blinks.
3. **Silent recognition** (section 2.3); if `unlock_needed`, offer to unlock. The PIN is
   sent once; a wrong PIN or cancel means no retry and the assistant stops.
4. **Touch only when needed:** for enrolment, "touch the blinking key". Then the self-check.
5. **Assignment choice:**
   - "a new key", or
   - "the key known as X" – offered only if X has **no** cryptographic or strong evidence,
     because a key with evidence would have been recognised. This is a *user assertion*:
     stored as `labels.assigned_by_user`, shown as such, and content read before stays
     `unconfirmed`.
   - A reset key: "Is this key X after a factory reset?" → a new entry with
     `predecessor: X`. Old content is **not** taken over, only linked for history.
6. **Name, colour and role** (Everyday, Spare, Travel, or free text) – organisational, no
   effect on the security rating.
7. **Result:** "Recognised by a cryptographic check on <date>" vs. "Named by you – not
   technically confirmed", with the limits in one sentence.

Safety:

- Every step is bound to the connection ID. If the key is unplugged or the ID changes, the
  assistant aborts and nothing is written.
- The commit is one history transaction, and it re-runs the silent check on the same
  connection first.
- Cancel at any step → no change.

### 3.2 Repair of possibly mixed entries [new] (priority 4)

A legacy entry of a model without serial is flagged `possibly_mixed` when:

- (a) the scanner ever sees two connections with the same legacy ID at the same time
  [new detection in 1.9], or
- (b) the user says so, or
- (c) always for legacy no-serial entries, with a softer wording ("could contain data of
  several keys of this model").

Flow:

1. Pick the entry → explanation: "Data may come from several keys; nothing will be deleted".
2. **Recognise one key at a time** (assistant 3.1) and do a fresh full read (or a probe on
   FIDO 2.0 keys).
3. **Three groups per item:**
   - *confirmed on this key* – found in the fresh read,
   - *known only from the old history*,
   - *not assignable*.

   An item missing from an **incomplete** read (probe partial, search stopped, section not
   supported) stays in "known only from old history", never "deleted".
4. **Preview** of the resulting entries, then apply.
5. **After applying:**
   - Each recognised key has its own entry with only its confirmed content.
   - The legacy entry becomes `archived` (read-only, visible under "earlier data") and keeps
     all its items with their original provenance.
   - `repair.state` records which new entries came from it.

Idempotence:

- `repair` is stored on the legacy entry. Re-running or resuming recognises keys by
  evidence, so no duplicates are created.
- Applying is one transaction, so an interruption before apply leaves no partial state.
- Unassigned items stay in the archive. They are shown in the account overview as "unclear
  (earlier data)" and never count as a confirmed backup.

### 3.3 Conflicts between computers [new] (priority 5)

**Automatic merge is justified only if** one connected key produces cryptographic proof, or
matches strong non-downgraded evidence, for **two or more** entries. That means the same
physical key was set up independently on two computers. Nothing else merges automatically:
not the same name, model, label, colour, QR label, or smart-card hints.

**Merge rules** (deterministic, so every computer reaches the same result):

- The survivor is the **lexicographically smallest** entry ID. The others become
  `aliases[old] = {into: survivor, at, reason: "same_key_proven"}`.
- Evidence and events: union.
- Labels: newest `set_at`; the other names are kept in `labels.previous` and shown once.
- Content: per field group, newest *confirmed* read wins. Unconfirmed content never
  overrides confirmed content.
- References (`replace.new`, lost-key progress, sync tombstones) are rewritten through the
  aliases. Unknown IDs are resolved via the alias chain (union-find, cycle-safe).

**User decision needed** (shown in the conflict view, never auto-resolved):

- Contradicting state: e.g. marked **lost** on computer A (at t1) while computer B read it
  after t1.
- A replacement running on one entry and not on the other, or pointing to different new keys.
- Two entries a user wants to merge **without** technical proof. This is allowed as a user
  assertion: content stays `unconfirmed` until the key is recognised.

**Conflict view** compares, per side:

- labels and evidence (kind, date, which computer),
- last read (time, computer, complete or not),
- lost state and replacement state,
- content differences (counts, with a detail list).

**Stale or older computers:**

- Incoming entries whose ID is an alias are folded into the survivor, so they cannot come
  back.
- Aliases are kept at least `FORGET_KEEP_DAYS` (400 days) and synced.
- 1.8 peers strip the new fields and keep writing to the legacy ID. 1.9 treats that data as
  `unconfirmed`/legacy and never as confirmed.
- The sync payload gets `app_version` [new]. If a peer has none or an older one, the sync
  view says "Computer X runs an older KeyMelier – update it for reliable key recognition".

**Stability:**

- Merges are idempotent and commutative: the survivor rule, the union of evidence and the
  per-field newest-wins.
- Re-syncing yields the same state. Tests run the merge in all orders.

## 4. Migration and sync concept

**Principle:** migration only ever **adds** fields. It never re-keys, deletes or
re-attributes content.

**On first start of 1.9:**

- Keep every `key_id`. `label` → `labels.name` (also kept in `label` for 1.8 peers).
- Evidence from what is already known:
  - YubiKey serial → `vendor_serial`,
  - USB serial → `usb_serial`, subject to the downgrade rules.
- Entries of models without any serial (legacy shared ID) → `integrity.possibly_mixed:
  "legacy_shared"`, with the softer wording.
- Their content provenance → `identity: "unconfirmed"`, with the read time taken from the
  existing fields (`sites_updated`, `inventory.*.updated`).
- Content of entries with strong evidence → `confirmed`. Behaviour stays unchanged for
  YubiKeys and keys with a real serial.

**Backup coverage (account model):** a key counts as protection only if **both** hold:

- the entry is `recognised`-capable (it has cryptographic or strong evidence), and
- the item's provenance is `confirmed`.

Otherwise the existing `unclear` statuses are used, with the new reason "identity not
confirmed". The upgrade note tells users that some coverage moves to "unclear" until each
such key is confirmed with one touch.

**Sync:**

- Payload: `app_version`; per entry `evidence`, `labels`, `integrity`, `provenance`,
  `repair`; top-level `aliases`.
- Evidence contains the credential ID and public key. These are not secret – useless without
  the key – but private. They stay out of diagnostics, inventory export and labels.
- `merge_sync` gains: an alias pass before merging, evidence union, and the rule that
  confirmed wins over unconfirmed.

**Without stored history** (history off, or `--stateless`): recognition needs stored
evidence, so every key is `unassigned` with the reason "history off". No enrolment is
offered.

## 6. Tests and acceptance

**Simulated authenticator** (WP2): it wraps its own credential IDs with a per-device secret.
Scripted behaviours:

- answers `up=false` silently,
- needs UV (credProtect 3 / alwaysUv),
- ignores `up=false` and waits for a touch (UPNEEDED keepalives),
- returns garbage signatures,
- times out,
- is reset (new device secret),
- is unplugged mid-command.

Several instances share one AAGUID, and all have no serial.

| Scenario | Expected |
|---|---|
| Two devices, same AAGUID, no serial | Two entries after enrolment. Neither recognises as the other. |
| Reconnect in another order / on another port / after a restart | Same entries recognised (evidence persists; the port is irrelevant) |
| Both connected at once | Each connection recognised separately. No smart-card hints are used. |
| Unplugged during recognition or assignment | Nothing written. State discarded. |
| UV required; PIN cancelled; wrong PIN | `unlock_needed`. Cancel → unchanged. A wrong PIN is sent once, then stop – no retry. |
| Silent recognition unsupported or timeout | `unsupported`/unresolved, the command is cancelled, never "different key", no merge |
| Invalid signature returned as success | Not recognised (proof = signature) |
| Key reset | All its credentials "not this" → `unassigned`. Old entry unchanged. Offer "after reset?" → new entry with `predecessor`. |
| Legacy mixed entry migration | Flagged. Coverage "unclear". No content re-attributed. |
| Repair interrupted and resumed; repeated | No duplicates. Legacy content preserved. Incomplete reads never count as deletions. |
| Independent setup on two computers | After sync, one connection proves both → automatic merge. Same survivor on both computers. |
| Offline changes, later sync; syncs repeated in all orders | Converges to one state; no new duplicates |
| Contradicting lost / replacement state | Conflict view. Nothing auto-resolved. References stay valid through aliases. |
| 1.8 peer in the sync folder | New fields survive on 1.9 computers. Legacy writes arrive as unconfirmed. Warning shown. |
| No stored history / stateless | `unassigned` with reason. No enrolment offered. |
| Diagnostics and inventory export | No credential ID, no public key, no evidence values – only counts per state |

**Acceptance criteria:** those of the assignment, mapped one-to-one onto the table above
(sections 1–4 of the assignment). The account-model tests gain "unconfirmed identity never
counts as backup".

**What simulation does not prove** (needs hardware, HARDWARE_TESTS.md): see section 7 – in
particular silent `up=false`, `credProtect` defaults, cancel behaviour and USB serial quality
per model.

## 7. Technical uncertainties to prove

| # | Assumption | How to prove |
|---|---|---|
| U1 | `getAssertion` with `up=false` is silent (no blink, no wait) on the supported models, including FIDO 2.0 keys | hardware matrix per model; the self-check (2.3 step 7) guards at run time |
| U2 | A non-discoverable credential with `rk=false` is usable without UV (credProtect ≤ 2) on these keys | hardware; the self-check detects credProtect 3 → `unlock_needed` |
| U3 | `authenticatorCancel` stops a key that waits for a touch, without side effects | hardware, all platforms (Windows WebAuthn-free HID path) |
| U4 | Credential IDs are stable and fit the storage limits (size) | simulator bounds plus hardware |
| U5 | USB serials: which vendors ship constant or shared values | collect from reports, and detect duplicates at run time |
| U6 | OpenPGP AID / PIV serials: mutability per implementation; CCID ↔ HID mapping | used only as hints and with a single key connected; document |
| U7 | 1.8 peers drop the new fields but keep the entries (IDs stay 16 hex) | upgrade/sync test with the 1.8.0 fixture (fixture still to be created) |

## 8. Minimum scope for 1.9 vs. later

**1.9 (all required):**

- the identity model and additive migration (WP1),
- recognition with signature proof and self-check (WP2),
- visible states and confirmed-only coverage (WP3),
- the assistant with labels, colour and role (WP4),
- the repair of mixed entries (WP5),
- sync aliases, proven automatic merge and a conflict view with user decisions (WP6),
- privacy and docs (WP7),
- hardware rows for two identical keys without serial.

**Later (evaluated separately, not needed for identity to work):**

- **Backup goals per account** – e.g. "on two active keys". Needs confirmed coverage from
  1.9 first. "Goal met" always refers to the available proof, never to guaranteed access.
- **Change history** – "account newly found / no longer found after a complete read /
  identity confirmed / assignment changed". Each event needs its source and time. Knowledge
  changes and changes on the key are separated by `read.complete` and provenance.
- **Printable labels** – name, colour or symbol, short inventory number, and an optional QR
  code with a random reference only. No account names, serials or credentials in it.
  Scanning opens an entry and never confirms identity.

**Constraints for all packages:**

- no automatic PIN retries,
- no deletion or reset of anything on a key,
- no silent re-attribution of stored data,
- technical proof and user assertion always stored and shown separately.
